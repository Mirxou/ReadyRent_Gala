## 7.2 إدارة الحوادث (Incident Management)

### 7.2.1 مستويات الخطورة

| المستوى | الوصف | وقت الاستجابة | وقت الحل | مثال |
|---|---|---|---|---|
| **P0 — Critical** | المنصة معطلة تمامًا | 15 min | 2 h | الخادم لا يستجيب |
| **P1 — High** | وظيفة حرجة معطلة | 30 min | 8 h | الدفع لا يعمل |
| **P2 — Medium** | وظيفة مهمة متأثرة | 2 h | 24 h | البحث بطيء |
| **P3 — Low** | مشكلة تجميلية | 24 h | 7 days | خطأ CSS في متصفح معين |

### 7.2.2 خطة الاستجابة لكل نوع حادث

#### انهيار الخادم (Server Down)
```
1. تحقق من UptimeRobot/Sentry (هل تنبيه حقيقي؟)
2. SSH للخادم
3. فحص: docker ps, docker compose logs, htop, df -h
4. إذا Docker يوقف: docker compose up -d
5. إذا OOM: زيادة RAM أو تحسين الاستهلاك
6. إذا disk full: تنظيف + توسيع
7. إذا مشكلة شبكة: فحص DNS, Cloudflare, provider status
8. التواصل مع المستخدمين (maintenance page إذا لزم)
9. كتابة Post-Mortem بعد الحل
```

#### تسريب بيانات (Data Breach)
```
1. تحديد النطاق: ما البيانات المُتسرَّبة؟
2. إيقاف النزيف: تعطيل الحساب/الـ API المتأثر
3. إخطار المستخدمين المتأثرين (قانونيًا في 72 ساعة)
4. فحص السجلات لتحديد المصدر
5. إصلاح الثغرة
6. مراجعة شاملة للأمان
7. إعداد تقرير قانوني
8. توثيق Post-Mortem
```

#### نزاع كبير (Mass Dispute)
```
1. تحديد السبب الجذري (منتج معيب؟ عملية احتيال؟)
2. إيقاف المنتج/البائع المتسبب مؤقتًا
3. إطلاق Escrow لكل الحجوزات المتأثرة
4. التواصل مع كل المستخدمين المتأثرين
5. مراجعة يدوية لكل نزاع
6. تحديث trust scores
7. مراجعة عملية ضبط الجودة
```
